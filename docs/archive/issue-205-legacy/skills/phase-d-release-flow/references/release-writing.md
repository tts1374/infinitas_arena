# リリース文・告知文の文章基準

## Objective / Boundary

利用者が更新内容と必要な操作を判断できる、平易な日本語の文章を作る。高校生・非技術者が、開発知識や事前説明なしで理解できることを成功条件にする。

allowed side effects は依頼された文章の作成・修正まで。公開済み本文の更新や外部への投稿は、その操作が依頼範囲にある場合だけ行う。文章完成だけで build・deploy・Release 公開へ進めない。

## 内容を選ぶ

- 対象 version・Release URL・対象 commit と、前回 release からの差分を確認する。利用手順・既知制限は現在の公開案内と関連 docs を根拠にする。根拠がない URL・asset 名・検証結果を作らない。
- 利用者が画面・操作・結果で実感できる変更を書く。「何が見やすくなったか」「何ができるか」「どの操作で起きていた不具合が直ったか」を具体化する。
- class/test/CI 名、内部 refactor、依存更新、保存処理の説明を変更点として並べない。専門語を言い換えただけの項目や、具体的効果のない「改善しました」で残さない。
- 更新に必要な操作、利用可否に影響する互換条件、既知の制限は保持する。必要な検証結果や公開物の識別情報は確認情報として分け、未確認事項を成功実績へ変えない。
- 現在確定した内容から構成し、会話で消えた案や不要な変更経緯を載せない。実際の差分、必要な制限、監査上の記録は隠さない。

## 媒体と確認

Release notes は既存テンプレートに合わせる。内部変更の列挙で空欄を埋めない。X 等の告知文は依頼された媒体・長さに合わせ、利用者向け変更を絞る。文字数制約がある場合は媒体の数え方を確認して実際に数える。

version・URL・配布案内の一致、利用者が取る操作の明確さ、未検証事項の扱いを確認して文章を返す。文章のみの依頼はここで終了する。
