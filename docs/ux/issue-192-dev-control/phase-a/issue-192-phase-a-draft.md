「実クライアントを開く」は並行して同一IDの模擬WSを残す意味ではない。Aは常に実連携。相手の実クライアント化は起動条件で選べるようにし、起動後の切替を実装するなら既存接続を停止して正規復帰する必要がある。安全な引継ぎを既存経路で行えなければ、新セッションで開き直す。この具体方式はBの実現性確認対象で、黙って製品契約を変えない。

## 操作フロー案

### 普段の実プレー＋模擬相手

1. 検証専用の起動からモード・人数・Host・入力経路を選ぶ。Aの実連携は参照先を読み取り専用で使用し、書き込むfixture先と分離する。
2. メイン画面と操作窓を開く。通常対戦はAを本人が操作し、B以降のReady・選曲を操作窓から行う。
3. 本人は実際のIIDXでプレー。相手には操作窓で模擬リザルトを投入。全ROUNDを正規の流れで通し、最終結果・再戦を確認する。
4. 画面の問題なら対象相手の実クライアントを開く構成で新規起動し、画面とsource別の隔離入力を確認する。
5. ログ・画像を保存して停止。検証用プロセスと予約入力を終了し、本人のIIDX・連携ソフト・通常アプリは停止しない。

### 合同プレー／大会を2曲続ける

1. 本人がHostを兼ねるか、模擬BをHostにするか起動時に選ぶ。兼任Hostを初版の例とし、専任Hostなど全役割を新規に拡張しない。
2. Hostが開催・譜面を確定しプレー開始。開催の毎曲Readyは表示しない。実クライアントは既存の自動監視・提出を通す。
3. B/Cは毎曲提出、Dだけ未提出待機にする。未提出を欠場として先に確定せず、Hostが待つか締め切るか選ぶ。
4. 締切後に欠場と曲別結果を確認し、Hostが次曲へ進む。同じ模擬入力方針を2曲目にも適用する。
5. Aを開催画面から移動しても監視・提出が続くことを実クライアントで確認。終了後は検証用履歴を再読込する。

### 接続と失敗

- 一時切断は対象の自動再接続を意図的に止めて再現し、「再接続」で同じID・復帰情報を使う。無条件の新規入室へ読み替えない。
- 明示退出は別ボタンで対象と影響を確認する。再入室条件は製品ルールに従い、退出直後の自由復帰を約束しない。
- Host切断中は既存の進行停止・提出継続を守る。復帰したか、期限経過で終了したかを観測し、ツールが強制解除しない。
- 対象曲・session・接続世代が変わったら予約入力をキャンセル。古い曲のスコアを新しい曲へ投入しない。
- 操作直後の「送信／投入済み」と受信した「受付済み」を別状態にする。timeoutや拒否理由を表示し、勝手に成功表示にしない。wireframeは表示例を短縮しており、最終ラベルの仕様はこの区別を優先する。
- ログ保存に失敗したら保存済みと表示せず、保存先・失敗内容・再試行導線を示す。操作窓を閉じるだけなら操作窓を隠し、セッション停止とは分ける（再表示可能にする案）。

## 保全・環境案

- 初版はローカル検証先のみ。開始時にloopbackのAPI/WS対応とsession所有を確認し、画面表示だけを保護策にしない。本番を選べる入力欄は設けない。
- 開発ビルドかつ明示した検証起動でのみ使用可能にする案。通常起動・配布版ではUIだけでなくコマンド経路も無効にする。既存E2Eフラグだけで配布版保護が完了したとはみなさない。
- sessionごとに設定・player ID・履歴・snapshot・fixture・ログを分離。本人Aの実連携ファイルは読み取りのみ、模擬ファイルはsession配下の許可先にのみ書く。
- 同じclientに対する操作窓の手動操作と既存自動scenario runnerを同時に走らせない。自動提出の方針も対象ごとに一つにする。
- 停止・やり直し前に影響を確認。自分が起動した検証プロセスだけを停止し、証拠は保持。失敗時に本人設定や既存履歴を自動復元・削除しない。
- 検証専用データを消す機能は初版の必須にしない。データを残して新sessionを作ればやり直せる。
